# 2026-08-30 — Raft Rumble: blind-fire camera, ragdolls, Windows desktop, hotspot rewrite

Five changes applied to `C:\xampp\htdocs\Raft-Game` (Flutter 3.47.1 / Dart 3.13.1, stable,
Flutter SDK at `C:\src\flutter`).

## 1. Blind-fire camera lock (was: aiming drag panned onto the enemy = free rangefinder)

- Root cause: `_updateAiming` in `lib/game/controller.dart` eased the camera toward
  `world.landingX(...)`, i.e. straight to the landing point.
- Fix: camera is anchored to the **shooter** (`BattleWorld.camAnchor`) and clamped as a
  **signed lead** over the anchor's raft (`clampToLock`). Near end keeps the shooter in
  frame (`camAnchorMargin = 130`); far end keeps every living enemy out of frame
  (`camEnemyMargin = 90`). New API: `lockedCenter` / `clampToLock` / `lockCam` /
  `holdCam` / `followCam`.
- Do NOT clamp an absolute centre-x — an incoming shot then drags the view off the
  shooter's own raft. That was the first (wrong) attempt.
- `trajectory()` preview capped at `trajectoryReveal = 0.34` of the flight, so the dotted
  arc can't be used as a rangefinder.
- `camOverhang = 420` lets `camFor` pan past the world edges. Needed on ultrawide: at
  viewWidth ≈ 1500 the camera otherwise cannot pull back far enough to hide a raft at
  x=1500, because cam was floored at 0.

## 3. Ragdoll + drowning

- `Crew` gained `offset / vel / tilt / spin / ragdoll / rest / drowned` and `knock()`.
- Integrated on its own fixed 60 Hz accumulator (`_bodyAccum` → `_stepBodies` →
  `_stepBody`) so both hotspot devices compute the identical result regardless of
  refresh rate.
- `Raft.deckY` re-derived to `waterY - width * thickness * 0.55` to match the renderer;
  added `deckHalf`, `feetPos(i)`, `crewPos(i)`. Overboard check must use
  `(crewOffset(index) + p.dx).abs()`, not `p.dx.abs()` — stations aren't at the centre.
- Drowning: feet past `waterY + drownDepth(14)` → hp = 0, splash Fx, `drowned = true`.
- **Tuning, measured** (`Crew.impactForce = (1.2 + damage*0.028) * (0.8 + 0.2*weight)`,
  `bodyLift = 0.25`, `bodyFriction = 0.72`): tennis/cluster slide 6, grenade 8, bomb 14,
  anchor 21. Only the anchor sweeps someone over the rail (medium raft: rearmost crew
  stands 41 from centre with 15 clearance, anchor slides 45 → overboard). Earlier punchier
  values threw someone over on *every* hit — don't go back to them.
- Renderer draws crew at their offset and rotates about the feet.

## 5. Hotspot multiplayer — rewritten

Old impl used an `HttpServer` + WebSocket upgrade; that handshake is what broke on real
hotspots (carrier NAT / captive portal / VPN tun / OEM proxy can rewrite or reject it).
Replaced with the Battle Ship approach (`C:\xampp\htdocs\Battle-Ship-Blitz-Mobile-Game`):

- Raw `ServerSocket`/`Socket` TCP, **newline-delimited JSON** (`SocketLink`), explicit
  framing because TCP is a stream — a `send` can be split or coalesced.
- UDP room beacon + scan on 50506 (game 50505), subnet-directed broadcast *and* global
  `255.255.255.255`, each send in its own try/catch so one ENETUNREACH can't kill it.
- Separate `_udp` (beacon) and `_scanUdp` (scan) — a shared field let a scan close the
  host's own beacon.
- `localIps` reports **all** addresses (`.first` advertised a mobile-data address the
  joiner couldn't reach); `_ingestRoom` dedupes on room code, prefers own subnet.
- Two-way `hello` handshake; START gated on `handshakeDone`.
- Android `WifiManager.MulticastLock` via `MethodChannel('raftrumble/multicast')`
  (`lib/game/multicast_lock.dart` + `MainActivity.kt`), `NEARBY_WIFI_DEVICES`,
  `CHANGE_WIFI_MULTICAST_STATE` in the manifest.
- Turn sync: `_turnSeq` + `_endedTurns` so an echoed `endTurn` is honoured once; only the
  device whose turn it is runs the countdown (`_ownsTurnClock`).

## 6. Follow-up — drag feel + camera tracks the shot in flight

Requested after the above shipped. Note that #2 below deliberately **reverses part of
fix #1**: the lock stays for the *aiming* phase, but is abandoned during *flight*.

### Drag controls

- `shapeAim(dx, dy)` returned a valid `AimTarget` for a **forward** pull (`dx < 0`),
  clamping the angle to `angleMin` regardless of drag direction. That is the "controls
  don't follow my direction" complaint. Now `if (dx < 4.0) return null;`, and
  `atan2(dy, dx)` replaced `atan2(dy, max(4.0, dx))` (the guard makes the max moot).
- One shared `smooth = 0.34` lerp made angle changes feel laggy, since the angle is what
  the player reads as "direction". Split into `smoothAngle = 0.55` (fast) and
  `smoothPower = 0.34` (steady, so the power meter isn't twitchy). `smooth = 0.45` kept
  for back-compat.
- The existing `Listener` input plumbing in `game_screen.dart` was already correct
  (raw pointer events, not `GestureDetector`, to dodge Flutter's ~18px pan slop) — no
  restructuring needed.

### Camera tracking during flight

- Aiming still uses `followCam` (clamped by `clampToLock`). Firing now uses a new
  `trackShot(worldX, vx, dt)` which bypasses the lock; `_updateResolving` calls a new
  `returnCamTo(playerIndex, dt)` to ease back to the next shooter.
- **The important bit — feed-forward.** A plain exponential ease trails a moving target by
  `vx / rate`. At full power that is ~400 world units, and `viewWidth` is only
  `422 * aspectRatio` (~195 portrait → ~1266 ultrawide), so the projectile flew clean off
  the side. Measured margins at rate 3.5, no feed-forward: **−41 at viewWidth 870, −379 at
  viewWidth 195** (negative = off screen).
- Fix: aim at `worldX + vx / shotTrackRate` — where the shot will be one time-constant
  from now. Steady-state error becomes **exactly zero**, and the worst-case clearance is
  then identical for every rate (verified 2.5 → 7.0 all give 65.7), so the rate can stay
  low and the pan stays smooth. Worst case is now the launch transient, not the lag.
- Feed-forward is the general pattern for any eased follow of a fast-moving target.
  Reach for it before raising the rate — a higher rate only shrinks the lag, it never
  removes it.
